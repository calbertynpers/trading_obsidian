# ADF-010: POC — FastAPI on ECS Fargate with API Gateway

**Priority:** Medium
**Status:** 🔴 Open
**Component:** `aws-deployment-framework`
**Type:** Research / POC
**Reported:** 2026-05-05
**Depends On:** [[ADF-002]]

---

## Summary

Proof of concept for running FastAPI applications on ECS Fargate behind API Gateway. Evaluates whether this pattern is suitable for the TIS webhook receiver and potentially the agent session (container-based agent with state).

## Goals

1. Deploy a minimal FastAPI app to ECS Fargate
2. Front it with API Gateway (HTTP API)
3. Measure cold start latency, request latency, and cost
4. Evaluate container-based agent session (persistent state in container)
5. Compare with Lambda + API Gateway for the webhook use case

## Questions to Answer

- What's the cold start time for a Fargate task with Python 3.14?
- Can we keep a persistent agent session in a Fargate container (vs Lambda's stateless model)?
- What's the cost comparison: Fargate (always-on) vs Lambda (per-invocation) for our traffic patterns?
- Does API Gateway → Fargate add meaningful latency vs direct ALB?
- Can MCP servers run as sidecars in the same Fargate task?

## Scope

- Minimal FastAPI app (health check + one POST endpoint)
- ECS Fargate task definition (Python 3.14 container)
- API Gateway HTTP API integration
- Load test with representative traffic (1 req/5s for price polling, bursty for webhooks)
- Cost estimate for 30 days

## Out of Scope

- Full TIS deployment (that's TIS-004+)
- Production hardening
- CI/CD integration

## Acceptance Criteria

- [ ] FastAPI app running on Fargate, accessible via API Gateway
- [ ] Latency measurements documented (p50, p95, p99)
- [ ] Cold start time measured
- [ ] Cost estimate for 30 days at expected traffic
- [ ] Recommendation: Fargate vs Lambda vs EC2 for each TIS component
