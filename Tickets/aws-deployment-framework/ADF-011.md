## Summary

Provision an Amazon EFS One Zone file system to serve as the shared trading knowledge base (Obsidian vault) accessible by EC2, Lambda, and the local Mac. This replaces the local-only Obsidian vault with a cloud-native shared filesystem.

## Architecture

```
Local Mac (Obsidian)              EFS One Zone              EC2 + Lambda
┌──────────────────┐         ┌─────────────────┐      ┌──────────────────┐
│ ~/Documents/     │◄─rclone─►│ EFS filesystem  │◄────►│ /mnt/vault/      │
│ obsidian/        │  bisync  │ (eu-north-1a)   │ NFS  │                  │
│ Trading_         │  5 min   │                 │mount │ EC2: Obsidian MCP│
│ KnowledgeBase/   │          │                 │      │ Lambda: EFS mount│
└──────────────────┘          └─────────────────┘      └──────────────────┘
```

## Why EFS One Zone

- **Single filesystem for all consumers** — EC2 and Lambda mount the same EFS. No sync lag between them.
- **Full POSIX support** — read, write, overwrite, delete. Obsidian MCP server works unchanged.
- **Lambda native mount** — Lambda can mount EFS directly (requires VPC configuration).
- **Low cost** — One Zone IA with lifecycle management: ~$0.043/GB-month. For ~5MB of markdown files, cost is negligible.
- **No Mountpoint limitations** — unlike S3 Mountpoint, EFS supports overwriting existing files.

## Resources

### EFS File System

| Property | Value |
|----------|-------|
| Name | `trading-vault-prod` |
| Type | One Zone (single AZ — eu-north-1a, same as EC2) |
| Performance Mode | General Purpose |
| Throughput Mode | Bursting (sufficient for small file I/O) |
| Lifecycle Policy | Transition to IA after 30 days |
| Encryption | At rest (AWS managed key) |

### Mount Target

| Property | Value |
|----------|-------|
| Availability Zone | eu-north-1a (same as EC2 instance) |
| Subnet | Same subnet as EC2 |
| Security Group | Allow NFS (port 2049) from EC2 SG and Lambda SG |

### Access Point (for Lambda)

| Property | Value |
|----------|-------|
| Path | `/vault` |
| POSIX User | `1000:1000` (match EC2 user) |
| Root Directory Creation | Enabled |

## EC2 Configuration

```bash
# Install EFS utils
sudo yum install -y amazon-efs-utils

# Create mount point
sudo mkdir -p /mnt/vault

# Mount EFS (with TLS encryption in transit)
sudo mount -t efs -o tls fs-XXXXXXXX:/ /mnt/vault

# Add to /etc/fstab for persistence across reboots
echo "fs-XXXXXXXX:/ /mnt/vault efs _netdev,tls 0 0" | sudo tee -a /etc/fstab

# Obsidian MCP server config points to /mnt/vault
```

## Lambda Configuration

Lambda functions that need vault access (agent-dispatcher, agent-executor) require:
- VPC configuration (same VPC/subnet as EFS mount target)
- EFS access point ARN in function config
- Mount path: `/mnt/vault`

```python
# In Lambda handler, vault files are at /mnt/vault/
with open("/mnt/vault/README.md") as f:
    index = f.read()
```

## Local Mac Sync (rclone)

```bash
# Install rclone
brew install rclone

# Configure rclone remote for EFS via SFTP (through EC2)
# Or: sync via S3 as intermediary (EFS → S3 → local)
# Simplest: rclone over SSH/SFTP to EC2's /mnt/vault/

# rclone bisync every 5 minutes via launchd
rclone bisync ~/Documents/obsidian/Trading_KnowledgeBase/ sftp-ec2:/mnt/vault/ \
  --create-empty-src-dirs \
  --resilient
```

**Alternative sync approach:** If SFTP through EC2 is too slow or complex, use AWS Transfer Family (managed SFTP endpoint for EFS) or sync via an S3 intermediary bucket.
