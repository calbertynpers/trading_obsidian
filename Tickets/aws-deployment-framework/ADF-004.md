## BDS Database Schema (migrated from SQLite)

```sql
-- bds_prod database

CREATE TABLE latest_snapshots (
    symbol VARCHAR(20) PRIMARY KEY,
    last_price DOUBLE PRECISION,
    price_change_pct_24h DOUBLE PRECISION,
    high_24h DOUBLE PRECISION,
    low_24h DOUBLE PRECISION,
    quote_volume_24h DOUBLE PRECISION,
    num_trades_24h INTEGER,
    mark_price DOUBLE PRECISION,
    funding_rate DOUBLE PRECISION,
    next_funding_time BIGINT,
    collected_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE snapshot_history (
    id BIGSERIAL PRIMARY KEY,
    symbol VARCHAR(20) NOT NULL,
    last_price DOUBLE PRECISION,
    price_change_pct_24h DOUBLE PRECISION,
    high_24h DOUBLE PRECISION,
    low_24h DOUBLE PRECISION,
    quote_volume_24h DOUBLE PRECISION,
    num_trades_24h INTEGER,
    mark_price DOUBLE PRECISION,
    funding_rate DOUBLE PRECISION,
    next_funding_time BIGINT,
    collected_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX idx_history_symbol_time ON snapshot_history (symbol, collected_at);

CREATE TABLE dynamic_watchlist (
    symbol VARCHAR(20) PRIMARY KEY,
    added_at TIMESTAMPTZ NOT NULL,
    added_by VARCHAR(50) NOT NULL
);
```

Implementation note: the deployed schema also includes a `schema_migrations` tracker table (added by `sql/bds/001_initial_schema.sql`) so future migrations can be applied incrementally without re-running prior ones.

## Approach (agreed 2026-05-04)

**AWS account:** `950858585111`, region `eu-north-1`. Single shared instance, multiple databases (one per service).

### Design choices

1. **CloudFormation owns infrastructure; SQL migrations own schema.**
   The template provisions the instance, networking, and Secrets Manager containers. Database/role creation and the BDS schema are applied via idempotent SQL scripts run from EC2 — *not* via CFN custom resources. This keeps stack updates safe and lets schema evolution proceed without touching infra.

2. **Master password generated by CloudFormation, never in git.**
   Use `AWS::SecretsManager::Secret` with `GenerateSecretString` for the master password, then reference it in the DB instance via a dynamic reference (`{{resolve:secretsmanager:...}}`). The application user `bds_app` gets a separately generated secret, populated by the bootstrap SQL script (or via `put-secret-value` after creation).

3. **Application user, not master, is what services use.**
   `bds_app` has CRUD-only on `bds_prod` — no DDL, no superuser. Master credentials stay in Secrets Manager, used only for migrations and admin tasks.

4. **Environment-parameterised from day one.**
   Template takes `Environment` (dev/test/prod), `DBInstanceClass`, `AllocatedStorage`, `MasterUsername` as parameters. Stack name and all resource names derive from `Environment`. See "Reusability" below for the multi-env story.

### Prerequisite state

- ✅ EC2 + security group `sg-0375487fef0e42eb8` exist (ADF-002)
- ✅ IAM role policy already grants `secretsmanager:GetSecretValue` on `/trading/*` — covers DB secrets too (ADF-003)
- ✅ Secret-path env-scoping decision (Option B): `/trading/{env}/...` from day one. ADF-003 paths migrated to match.

### Workflow

1. Deploy stack: `aws cloudformation deploy --template-file templates/rds-postgres.yml --stack-name trading-db-prod --parameter-overrides file://params/rds-prod.json --region eu-north-1 --capabilities CAPABILITY_NAMED_IAM`
2. SCP `init-bds-db.sh` + `sql/bds/*.sql` to EC2; run `init-bds-db.sh` (uses master creds from Secrets Manager)
3. Run `verify-rds.sh` from EC2 — confirms `bds_app` can SELECT/INSERT on the schema
4. Update ADF-005 to consume `/trading/prod/db/bds-credentials` from Secrets Manager
5. Update this ticket + Ticket Index with completion status

### Reusability model (see chat 2026-05-04)

- **Infra changes** (instance class, storage, backup retention) → re-run `aws cloudformation deploy` with updated params. CFN diffs and applies in place.
- **Schema changes** → add `sql/bds/00N_xxx.sql`, run via migration runner from EC2. Never via CFN.
- **New environment** (e.g. `dev`) → new param file `params/rds-dev.json`, new stack `trading-db-dev`. Same template, no fork.
- **New service database** (TIS, TMS) → add `sql/{service}/001_initial_schema.sql` + per-service `init-{service}-db.sh`. Same RDS instance, new database + new app user + new Secrets Manager entry.

### Decisions / non-obvious bits worth knowing later

1. **Egress rule lives in the RDS stack, not the EC2 stack.** Standalone `AWS::EC2::SecurityGroupEgress` on the EC2 SG, destination = DB SG. Avoids a cross-stack `ImportValue` cycle. Scoped lifetime: tear down RDS stack → egress rule disappears too.
2. **DB endpoint discovery via Secrets Manager, not CFN/RDS APIs.** `SecretTargetAttachment` merges `host`/`port`/etc into the secret JSON. Means EC2 services need only `secretsmanager:GetSecretValue` on `/trading/*` (which the role already has).
3. **psql variable substitution does NOT work inside `$$ ... $$` blocks or with `-c`.** The init script uses heredoc + `:'var'` for the password to avoid escaping pain — the CFN-generated password may contain single quotes since `ExcludeCharacters` only excludes `"@/\` and space.
4. **`schema_migrations` is bootstrapped by the first SQL file itself.** No separate "init the migrations table" step. The init script handles the chicken-and-egg by checking whether the table exists before querying it.
5. **Engine version was 16.13 not 16.4** — `aws rds describe-db-engine-versions --engine postgres --region eu-north-1` is the source of truth; default in the steering doc/ticket was outdated.
6. **EC2 needed `postgresql16` package** — not in AL2023 base image. Installed via `sudo dnf install -y postgresql16` (client only, ~1 min).
