## Summary

Build a POC demonstrating the end-to-end Pine Script generation and alert pipeline. The agent analyses a symbol on demand, identifies key levels and a setup, generates a ready-to-paste Pine Script indicator that draws the setup on a TradingView chart, and wires `alertcondition()` blocks that fire structured JSON webhooks to TIS when price interacts with each level.

The POC exists to:
1. Confirm the Pine Script generation quality and chart rendering is usable
2. Validate the webhook payload format consumed by TIS-007
3. Identify any gaps in the TIS-007 spec before full implementation
4. Establish the agent prompt template for Pine Script generation requests

---

## Pine Script Generation Workflow

```
User: "Draw the FTP setup for TAOUSDT"
        ↓
Agent pulls TradingView MCP analysis (daily + 4H)
        ↓
Agent identifies:
  - Key resistance levels
  - Support zones
  - Entry zone (rejection confirmation range)
  - Stop loss level
  - TP1 / TP2 / TP3 targets
        ↓
Agent generates Pine Script v5 indicator:
  - hline() or line.new() for each level
  - box.new() for entry and support zones
  - label.new() for level annotations
  - alertcondition() for each level with structured JSON message
        ↓
Agent outputs:
  1. The Pine Script (paste into TV as indicator)
  2. Summary of levels drawn
  3. Webhook alert setup instructions (which alertconditions to enable in TV)
```

## Pine Script Output Structure

The generated script shall follow this template:

```pine
//@version=5
indicator("[TIS] TAOUSDT FTP Setup — 2026-04-26", overlay=true)

// ─── LEVELS ──────────────────────────────────────────────────────────────────
float resistance_1 = 260.00
float entry_zone_top = 258.00
float entry_zone_bot = 255.00
float support_1 = 225.00
float stop_loss = 210.00
float tp1 = 240.00
float tp2 = 225.00
float tp3 = 210.00

// ─── VISUALS ─────────────────────────────────────────────────────────────────
hline(resistance_1,  "Resistance ($260)",  color=color.red,    linewidth=2, linestyle=hline.style_solid)
hline(support_1,     "Support ($225)",     color=color.green,  linewidth=2, linestyle=hline.style_dashed)
hline(stop_loss,     "Stop Loss ($210)",   color=color.red,    linewidth=1, linestyle=hline.style_dotted)
hline(tp1,           "TP1 ($240)",         color=color.teal,   linewidth=1, linestyle=hline.style_dotted)
hline(tp2,           "TP2 ($225)",         color=color.teal,   linewidth=1, linestyle=hline.style_dotted)
hline(tp3,           "TP3 ($210)",         color=color.teal,   linewidth=1, linestyle=hline.style_dotted)

// Entry zone box
var box entryBox = box.new(bar_index, entry_zone_top, bar_index + 500, entry_zone_bot,
     border_color=color.orange, bgcolor=color.new(color.orange, 85))

// ─── ALERTS ──────────────────────────────────────────────────────────────────
alertcondition(close >= resistance_1,
     title="Resistance Touch",
     message='{"passphrase":"${WEBHOOK_PASSPHRASE}","symbol":"TAOUSDT","source":"pine_script","setup_id":"taousdt-ftp-20260426","level_label":"resistance_1","level_price":260.00,"trigger_price":"{{close}}","level_type":"resistance","setup_type":"ftp","urgency":"alert","message":"TAOUSDT has touched resistance at 260.00. FTP setup active — monitor for rejection confirmation before shorting.","direction":"short"}')

alertcondition(close <= support_1,
     title="Support Touch",
     message='{"passphrase":"${WEBHOOK_PASSPHRASE}","symbol":"TAOUSDT","source":"pine_script","setup_id":"taousdt-ftp-20260426","level_label":"support_1","level_price":225.00,"trigger_price":"{{close}}","level_type":"support","setup_type":"ftp","urgency":"alert","message":"TAOUSDT has reached support at 225.00. Assess hold vs stop decision.","direction":"neutral"}')

alertcondition(close <= stop_loss,
     title="Stop Breach",
     message='{"passphrase":"${WEBHOOK_PASSPHRASE}","symbol":"TAOUSDT","source":"pine_script","setup_id":"taousdt-ftp-20260426","level_label":"stop_loss","level_price":210.00,"trigger_price":"{{close}}","level_type":"stop","setup_type":"ftp","urgency":"action_required","message":"TAOUSDT has breached the stop level at 210.00. Review position immediately.","direction":"neutral"}')
```

## Agent Prompt Template for Pine Script Generation

The agent shall respond to Pine Script generation requests using this structure:

**Input:** `"Draw the [setup_type] setup for [SYMBOL]"`

**Agent process:**
1. Call TradingView MCP for daily and 4H analysis on the symbol
2. Identify resistance, support, entry zone, stop, and TP levels from indicator data
3. Cross-reference with current position context (from BDS enrichment if available)
4. Generate Pine Script v5 indicator following the output structure above
5. Output the script + a human-readable level summary + TV alert setup instructions

**Required output sections:**
- The Pine Script code block (ready to paste)
- Level summary table (label, price, type, alert urgency)
- TV setup instructions (where to add the indicator, how to enable alerts, which webhook URL to configure)

## Implementation Notes


### Spec deviations during implementation (2026-04-27)

Surfaced and accepted while building Tasks 1–7. Captured here so the spec author can fold them back into design.md / tasks.md or override.

1. **pytest config — `--import-mode=importlib`, no `tests/pine_generator/__init__.py`.** Task 1.2 said add `__init__.py` to both `src/pine_generator/` and `tests/pine_generator/`. With both present, pytest's rootdir-based sys.path injection makes `tests/pine_generator/` shadow the source package (`ModuleNotFoundError: pine_generator.models`). Fix: remove the test-side `__init__.py` and switch pytest to `--import-mode=importlib`. Net effect: tests still discoverable, no collision; tests/ structure still mirrors src/.

2. **`analyse_symbol(request, provider)` instead of `analyse_symbol(request)`.** Design.md shows the function with a single arg, but task 7.6 requires mocking MCP responses. Without dependency injection this would need global patching. Added `provider: MCPDataProvider` (Protocol) as a second arg — testable via injection, leaves real MCP wiring as a provider implementation (TIS-007 territory).

3. **Invented `MCPDataProvider` data contract.** Design.md and requirements don't pin down MCP response schemas. Defined a minimal contract with methods `tv_daily_analysis`, `tv_4h_analysis`, `bds_snapshot`, `bds_position` returning dicts with documented keys (`high`, `low`, `bollinger_lower`, etc.). Mapping live MCP payloads onto this shape is a provider-boundary concern deferred to TIS-007.

4. **Hypothesis property tests deferred from Tasks 5/7 to Task 12.** The optional `*` Hypothesis variants of Properties 1–3 and 5–10 are currently covered by parametrized concrete examples per setup type. Hypothesis-driven versions will be added in Task 12.2 when the shared strategy module lands in `tests/pine_generator/conftest.py`, to avoid writing strategies twice. Net property coverage is solid; only the random-input dimension is pending.

5. **Level identification heuristics are POC-grade.** FTP uses daily_high + ±0.5%/2% buffer; mean reversion uses Bollinger lower (or daily_low fallback) with stop at `zone_bottom * 0.99` to satisfy Property 3. Real heuristic tuning is part of POC execution (manual validation per Req 10.2/10.3) and any findings should land in the Gap Report (Req 9).

User confirmed all five points are acceptable on 2026-04-27.

## Implementation Notes



### Live BTC dry-run + scope additions (2026-04-28)

> *Migrated from IDS-003.md — these notes were originally filed under the wrong ticket.*

Ran the pipeline end-to-end against real MCP data for BTCUSDT (all three setup types). Pipeline survived live data and produced compilable-looking Pine Script. Captured the run as `scripts/dry_run_btc.py` for reproducibility. Findings split into "delivered now" and "additional scope".

**Delivered now (2026-04-28):**
- **Float-formatting fix.** Real-world arithmetic was producing reprs like `76387.95568049999` and `74871.597754305`. Added `format_price()` and `round_price()` helpers in `script_generator.py` keyed off price magnitude (2 decimals ≥100, 4 decimals ≥1, 6 decimals ≥0.01, else 8). Pine output and JSON payloads now both clean. All 90 tests still pass.
- **FTP heuristic tightening.** Original entry zone (`resistance × [0.98, 0.995]`) straddled current price for BTC, breaking FTP "wait for retest" semantics. Tightened to `resistance × [0.99, 0.998]` so the zone sits just below resistance and above any reasonable current price. Also added a `FTP_MAX_TP_DISTANCE_PCT = 0.15` filter so pivot S2/S3 levels (frequently 17–25% away on BTC) are no longer suggested as TPs. For BTC with resistance=77478, current=76064: zone now [76703, 77323], TPs filtered from 3 → 1 (only the in-range pivot R1 at 74522 survives).

**Additional scope identified — split out to separate tickets:**
1. **Real `MCPDataProvider` implementation** → [[IDS-005]]
2. **Distance-filtering for mean-reversion TPs** — apply same `MAX_TP_DISTANCE_PCT` pattern. Nice-to-have polish.
3. **Pine v5 compilation still unverified** — covered by manual-test plan in `docs/poc-execution.md`. BTC POC validated successfully on 2026-05-01.
4. **Output formatter / Pine script price-format divergence** — reconcile by routing table through `format_price()`. Nice-to-have polish.
5. **TV pivot-naming clash** — cosmetic; noted in `docs/poc-execution.md`.

**Demo readiness assessment:** Mean-reversion setup is the cleanest output for a live demo; FTP is now defensible after the heuristic fix; SR_Map is fine but visually noisy with 6 stacked `hline`s.
