## 1. Summary

Define and prototype a **daily sweep methodology** that walks the entire ~600-symbol Binance USDT-M perpetuals universe over a rolling 7-day window, surfacing bottom-fishing candidates that are then sized using a new **3-tier risk-profile system** (Tier A $30 / Tier B $20 / Tier C $10 collateral, all at 20x leverage).

This is a manual/semi-automated precursor to the eventual autonomous Alpha Scanner ([[ALS-001]]). It runs as a daily ritual — first pass cheap and broad, deep dive only on promotions.

---

## 2. Motivation

The existing [[Strategies/Long Bottom-Fishing Strategy]] surfaces a small handful of named candidates per session, hand-selected from headline coins. Two gaps:

1. **Coverage gap.** ~600 perps exist; we currently look at the same 30–50 repeatedly. Bottom-fishing alpha sits disproportionately in coins nobody is watching.
2. **Sizing gap.** Current strategy says "size small, low leverage". In practice every entry has been ad-hoc. There is no calibrated size-by-conviction rule, so capital is mis-allocated — too much in marginal candidates, not enough in conviction names.

The sweep solves coverage. The risk-tier system solves sizing.

---

## 3. Risk-Tier Sizing System

See [[Strategies/Long Bottom-Fishing Strategy#Risk-Tier Sizing Profile (added 2026-05-03)]] for the full definition. Summary:

| Tier | Collateral | Leverage | Notional | When |
|------|-----------:|---------:|---------:|------|
| A — Conviction | $30 | 20x | $600 | Utility + narrative + rotation + MM history all align |
| B — Volatility/Lottery | $20 | 20x | $400 | Moderate conviction; some downside risk; or asymmetric lottery move |
| C — Long-tail Skin-in-Game | $10 | 20x | $200 | Low pump-probability but worth optionality |

**Default-and-promote:** every candidate that clears the sweep enters at Tier C. Promotion to B/A requires a deep-dive note documenting the upgrade rationale.

**Leverage invariant:** 20x always. Conviction is expressed as collateral, not leverage. This keeps liquidation geometry uniform and decouples sizing from risk-of-ruin geometry.

## 4. Daily Sweep Methodology

### 4.1 Universe and partitioning

- Source the live USDT-M perpetuals universe from `binance-data-collector` / `binance-position-tools`. Estimated ~600 symbols today; will drift as Binance lists/delists.
- **Partition into 7 daily slices**, ~85–90 symbols each. Partitioning rule must be deterministic and rotation-stable so the same coin lands in the same day's slice each week, allowing week-on-week comparison.
  - **Proposed key:** alphabetical buckets (e.g. A–C, D–F, …). Simple, stable, easy to audit.
  - Alternative: hash(symbol) mod 7. More uniform load but harder to eyeball.
- Held positions and existing watchlist coins are always examined regardless of slice (no double-tax — they're either upgraded, demoted, or closed; not re-entered).

### 4.2 First-pass filter — high-level, cheap

Run automated against each symbol in today's slice. Goal: drop ~80% of the slice in seconds, not minutes. Data sources are limited to **what BDS + binance-position-tools already expose** to keep the pass cheap.

Hard-knockout criteria (any of these → discard):
- 24h volume < $1M (illiquidity)
- Funding rate > +0.5% (longs pay too much)
- Coin price > 50% above ATL **and** > 30% above 30-day low (not actually near a bottom)
- Already held in a meaningful position (route to position-management workflow instead)

Pass-through criteria (forward to deep-dive queue):
- ATH distance ≥ 70%
- ATL proximity ≤ 25%
- Funding ≤ +0.1%
- 7d move ≤ 0% (no momentum chasing — sweep is for bottoms)

Borderline → flag for manual eyeball, don't auto-discard.

### 4.3 Deep-dive — slow, expensive, narrow

Only candidates that survive the first pass go through deep-dive. Target: ≤ 10 deep-dives/day on average.

Deep-dive pulls in additional sources (CoinGecko Scanner, TradingView MCP, narrative cross-reference):
- Tokenomics (FDV/MCap, unlock schedule)
- Narrative bucket — does this fit an active narrative per [[Building Map]]?
- TA confluence (multi-timeframe, RSI, BB, key levels)
- MM history check — past pump-and-dump cycles, whale-wallet patterns
- Funding history (not just spot funding) — has it sat in negative funding?
- OI structure — flat OI through a dump = passive accumulation; rising OI = trapped longs

Output of deep-dive is a tier assignment (C / B / A / pass) and, if non-pass, a coin note in `Coins/[SYMBOL].md` per the existing convention.

### 4.4 Daily output artefact

Each sweep produces a daily note in `daily/YYYY-MM-DD.md` (or appended) with sections:

- **Slice today:** alphabetical range covered
- **First-pass survivors:** list with the trigger criteria met
- **Deep-dive results:** per-coin tier assignment and rationale
- **Promotions/demotions** of existing positions noticed during the sweep
- **Next-day slice preview** (what's coming, in case rotation is starting in that bucket)

### 4.5 Weekly rollup

End of week (Sunday): write a `daily/YYYY-MM-DD.md` rollup section "Week's bottom-fishing review" with the full week's tier-A and tier-B promotions, and a coverage-completeness check (did we actually hit every slice or did Tuesday get skipped?).

## 5. POC Implementation Plan

This ticket is **spec only**. POC implementation suggested in three small steps so we can stop and re-evaluate after each:

### Phase 1 — Manual sweep, no tooling
- Run the methodology by hand for 1 week using only existing MCP tools (binance-position-tools, tradingview-mcp, coingecko-scanner)
- Output goes straight into daily notes
- Goal: validate the funnel ratios (does ~85/day → ~10 deep-dives → ~2 entries actually hold?) and surface workflow friction

### Phase 2 — First-pass automation
- Small Python script (lives in `binance-data-collector` repo or new `alpha-scanner` repo) that pulls today's slice and runs the first-pass filter
- Output: a CSV / markdown table of survivors → pasted into the daily note for deep-dive review
- Still manual deep-dive

### Phase 3 — Tier tracking + budget
- Schema for tracking active tier-A/B/C positions and total collateral committed
- Budget guardrail: e.g. cap total bottom-fishing collateral at 15–20% of wallet
- Per-coin promotion/demotion log

Phases 2 and 3 fold into [[ALS-001]] when the autonomous service comes online.

## 6. Margin Budget Model

To prevent tier-C sprawl from eating capital:

- **Working assumption:** ~600 perps × 7-day sweep × ~10% deep-dive rate × ~30% become tier-C entries = ~18 fresh tier-C positions/week → $180/week tier-C collateral.
- After 4 weeks of unmanaged accumulation: ~$720 in tier-C alone, before any tier-B or tier-A promotions.
- **Mitigation:**
  - Hard cap on tier-C count (e.g. 30 active) — beyond which oldest underperformers must be closed before new ones open.
  - Mandatory weekly tier-C cull — anything not promoted to B in 4 weeks and showing no thesis progression closes.
  - Wallet-level cap: total bottom-fishing collateral ≤ 20% of wallet equity.

These are starting numbers — Phase 1 will calibrate them.

## 7. Open Questions / Concerns

1. **20x leverage at C-tier — is this actually right?** $10 collateral × 20x = $200 notional. A 5% adverse move liquidates the position (in isolated; cross is different but bleeds the account). For a "lottery ticket / skin-in-game" position, 20x might be over-engineered — 5x or 10x at $20–$40 collateral might give the same notional with more breathing room. Worth pressure-testing in Phase 1.
2. **Cross-margin compounding risk.** All Binance positions are cross-margin per [[Strategies/Account Configuration]]. 30+ tier-C lottery tickets at 20x compounding small adverse moves can trigger account-level liquidation cascades. The micro-position-scanner already lives at 1x for this reason. Need to think hard about whether 20x cross is compatible with a 30-position-deep tier-C book.
3. **Funding drag.** Even at neutral funding, holding 30+ longs through 90 days of squeeze costs real money. Funding budget should be a tier-C close criterion.
4. **Universe drift.** Binance lists/delists weekly. Slice partitioning needs to handle new coins gracefully (assign by alphabetical bucket, append to today's slice if new this week).
5. **Coverage vs. quality trade-off.** Forcing 85/day means some days the slice will be junk and we'll end the day with zero candidates. Resist the urge to promote a marginal candidate to "fill quota" — the value is in the *coverage*, not in entry count.
6. **Interaction with [[Projects/micro-position-scanner]].** That project already runs ~94 long-bias positions at 1x leverage. The new tier system at 20x is a separate book. Should the micro-scanner positions be *re-classified* into tiers (and re-leveraged), or run as a parallel book? Recommend: keep micro-scanner as 1x discovery layer; tier-system is the *conviction layer* you graduate into when discovery surfaces a real signal.
7. **Tier ladder vs. tier mapping.** Is a coin promoted *gradually* (C → B → A as evidence accumulates) or *jumped* (deep-dive assigns A directly when all criteria align)? Recommendation: allow either, but document *why* on the coin note.
8. **Sweep automation language/repo.** Lives in `alpha-scanner/` (new repo) or as a script under `binance-data-collector/`? ALS-001 says new service. POC scripts could ride in BDS short-term and migrate when ALS-001 is built.
