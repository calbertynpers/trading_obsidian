# BDS-013: Reduce get_income_history Payload Size

**Priority:** Medium
**Status:**  🟢 Done — Merged
**Component:** `binance_data_collector.position_mcp_server`
**Type:** Enhancement
**Reported:** 2026-04-22
**Merged:** 2026-04-23 (commit `de97e7b`)

---

## Summary

Reduce the payload size of `get_income_history` by adding optional filtering and summary-only params. A 24h unfiltered call returns ~300KB / ~900 records grouped by symbol. Only ~4 symbols had closed-trade activity; the remaining ~86 symbols contributed near-zero funding dust on open positions. This overflows LLM context and inflates token usage. The useful signal is ~20% of the payload.

## Problem

The current `get_income_history` tool returns every income record for every symbol in the time window. For a portfolio with 90+ positions, this means hundreds of funding fee records for symbols with no trading activity — just dust. The summary block alone answers most "how did I do today" questions, but the full records_by_symbol dict dominates the response.

## Proposed Params (all optional, backward-compatible)

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `summary_only` | `bool` | `False` | Return only the summary block and round_trip_symbols list. ~95%+ payload reduction. |
| `top_n_per_symbol` | `int \| None` | `None` | Cap records per symbol (most recent first). Useful for high-fill symbols like NAORIS (313 records in 48h). |
| `min_abs_amount` | `float \| None` | `None` | Filter out funding dust below threshold (e.g., 0.001 filters sub-penny entries). |
| `exclude_open_positions` | `bool` | `False` | Exclude symbols with no REALIZED_PNL in the window (funding-only noise from open positions). |

### Optional Breaking Change for Consideration

Make `summary_only=True` the default with an `include_records=True` opt-in. Most "how did I do today" questions are answered by the summary alone. This would be a breaking change but dramatically improves default UX.

**Decision:** Not adopted. All four params default to backward-compatible values (`False`/`None`) so existing callers see identical behaviour.

## Acceptance Criteria

- [x] All four new params accepted and reflected in the tool schema
- [x] `summary_only=True` returns <5KB for a typical 24h call

- [x] Param combinations compose correctly (e.g., `exclude_open_positions + top_n_per_symbol`)
- [x] Tests cover each param individually and in combination

## Implementation Notes

- Filters are **post-fetch** — the underlying Binance API call is unchanged. Filtering happens in-process on the grouped response.
- Filter application order: `exclude_open_positions` → `min_abs_amount` → `top_n_per_symbol` → `summary_only`.
- Summary totals (`total_pnl`, `total_funding`, etc.) are computed **after** filtering so the summary always matches the visible records. This was a deliberate choice — callers passing filters want the summary to reflect what they asked for, not the raw window.
- Validation: `top_n_per_symbol >= 1` and `min_abs_amount >= 0`. Invalid values raise `ValueError`, which the `@retry` decorator wraps in `RetryError` (same pattern as existing `income_type` validation).
- 18 new tests added (3 validation, 12 filtering behaviour, 3 MCP-layer). Full suite: 97/97 passing.
