## Summary

Add an MCP tool to the Binance Data Collector that allows external callers (TIS, agents, Alpha Scanner) to programmatically add symbols to the collector's tracked watchlist at runtime, without restarting the service or editing the YAML config.

## Problem

The Binance Data Collector currently tracks a fixed set of symbols defined in `config/collector_config.yml`. The TIS watchlist may contain symbols the collector doesn't track, meaning `get_snapshot` won't return prices for those symbols. There's no way to dynamically add symbols to the collector's tracking without editing config and restarting.

BDS-015 addresses this for active positions (auto-sync from Binance), but there's no mechanism for other services to explicitly request tracking of a specific symbol.

## Proposed Tool

```
Tool: add_to_watchlist
Parameters:
  symbols: list[str]  — e.g. ["ZKJUSDT", "NAORISUSDT"]
Returns:
  added: list[str]    — symbols newly added
  already_tracked: list[str] — symbols already in watchlist
```

**Behaviour:**
- Adds symbols to the in-memory watchlist immediately
- New symbols start appearing in `get_snapshot` on the next poll cycle
- Does NOT modify the YAML config file (in-memory only, same as BDS-015 approach)
- Idempotent — adding an already-tracked symbol is a no-op
- Logged at INFO level when new symbols are added

## Use Cases

- **TIS**: When a new symbol is added to the TIS watchlist, the TIS can call `add_to_watchlist` to ensure the data collector tracks it
- **Alpha Scanner**: When ALS-001 identifies a candidate, it can register the symbol for price tracking
- **Agent**: When the agent opens a position on a new symbol, it can ensure historical data collection starts

## Acceptance Criteria

- [ ] New MCP tool `add_to_watchlist` accepts a list of symbols
- [ ] Added symbols appear in `get_snapshot` within one poll cycle
- [ ] YAML config file is not modified
- [ ] Idempotent — re-adding an existing symbol returns it in `already_tracked`
- [ ] Logged at INFO when new symbols are added

## Implementation Decisions (2026-04-25)

Logged during spec-review pass on `feat/bds-019-add-to-watchlist` so future troubleshooting has the rationale at hand.

### Q1 — Bucket precedence when a symbol is in YAML but not in `dynamic_watchlist`
**Decision: mutually exclusive (option a).**
A symbol present in the YAML watchlist is reported in `already_tracked` only — even if the call resulted in a fresh row in `dynamic_watchlist`. `added` reflects symbols *the caller caused tracking to begin for*, not raw DB inserts. UX over DB-mechanics.

### Q2 — Should YAML-tracked symbols still be written to `dynamic_watchlist`?
**Decision: yes, write them anyway (option i).**
The dynamic table is the single source of truth for "callers explicitly registered this symbol." Suppressing the insert would lose that signal if the YAML watchlist later changes. Cost is one harmless row per overlap. The `_filter_watchlist()` union dedupes regardless.

### Q3 — INFO logging on new additions
**Decision: log at INFO when new symbols are added.**
The original ticket required this; the Kiro spec dropped it. Restored. Log line goes in the MCP tool layer (after a successful `add_symbols()` call), formatted similarly to other tool log lines. Skip logging when nothing was newly added.

### Q4 — Race in `WatchlistWriter.add_symbols()`
**Decision: drop the SELECT-then-INSERT pattern from `tasks.md:33`. Use `INSERT OR IGNORE` and detect inserts via `cursor.rowcount` (or `total_changes` delta).**
Functionally identical, no race under concurrent writers, simpler code. The task wording is treated as illustrative, not normative.

### Q5 — `WatchlistWriter.get_all_symbols()` has no caller in the BDS-019 path
**Decision: keep it.**
Required by Req 4.4 and likely useful for future tooling (e.g. an `mcp` `list_dynamic_watchlist` tool, debugging, or test introspection). Cost is ~3 lines.

### Q6 — `WatchlistWriter.close()` lifecycle
**Decision: define `close()` but rely on process exit, matching the existing `_db: DatabaseReader` pattern in `mcp_server.py`.**
No explicit shutdown hook in `mcp_server.py` today. Adding one for `_ww` only would be inconsistent. If a shutdown lifecycle is added later, both should hook into it together.

### Notes for the implementer
- Test coverage for "table missing" branch in `DatabaseWriter.get_dynamic_watchlist()` is only reachable on pre-BDS-019 databases — both writers create the table on init in post-BDS-019. The branch still needs the test (Req 5.3 / 7.3); just construct a DB without it explicitly.
- A YAML-only symbol passed to `add_to_watchlist` will land in `already_tracked` (per Q1) **and** create a `dynamic_watchlist` row (per Q2). Property test P4 must exercise this case explicitly so the asymmetry between "DB write occurred" and "tool reported as added" is verified.

### Schema

```sql
CREATE TABLE IF NOT EXISTS dynamic_watchlist (
    symbol   TEXT PRIMARY KEY,
    added_at TEXT NOT NULL,    -- ISO 8601 UTC
    added_by TEXT NOT NULL     -- caller identifier
);
```

Created by **both** `DatabaseWriter.initialize()` and `WatchlistWriter.initialize()` so whichever process starts first sets up the table.

### MCP tool surface

```python
add_to_watchlist(
    symbols: list[str],
    added_by: str = "mcp_client",
) -> dict
```

**Returns:**

```python
{
    "added":            list[str],   # symbols newly registered for tracking
    "already_tracked":  list[str],   # already tracked via dynamic table OR YAML
    "dynamic_count":    int,         # total rows in dynamic_watchlist after call
}
# or
{ "error": "..." }
```

**Behaviour:**
- Symbols normalised to uppercase before insert.
- `INSERT OR IGNORE` for idempotency; `cursor.rowcount` distinguishes inserted vs ignored (no SELECT-then-INSERT race).
- A symbol that's in the YAML watchlist always lands in `already_tracked` (per Q1 decision), even though the row is inserted into the dynamic table (per Q2). This keeps `added` semantically aligned with "the caller caused tracking to begin," not "a DB row was created."
- INFO log emitted on new additions (per Q3 decision); silent when nothing was newly added.
- Empty input returns descriptive error; missing DB returns descriptive error; unexpected exceptions return sanitised error message (no internal paths leaked).
- Lazy-initialises `WatchlistWriter` on first tool call (mirrors `_get_db()` pattern).

### Effective watchlist on the collector

```python
effective = set(self._config.watchlist) | set(dynamic_symbols or [])
if not effective:
    return snapshots          # backward-compat: empty union → track all
return [s for s in snapshots if s.symbol in effective]
```

Read each poll cycle (default 60s), so a newly-registered symbol starts being collected within one interval. Read failures degrade gracefully to YAML-only.

### Backward compatibility

- An empty or missing `dynamic_watchlist` table produces identical behaviour to pre-BDS-019.
- `_filter_watchlist()` signature change is backward-compatible (`dynamic_symbols: list[str] | None = None`).
- `DatabaseWriter.get_dynamic_watchlist()` swallows `OperationalError` and returns `[]` when the table doesn't exist.
- No new dependencies — `aiosqlite` and `hypothesis` were already in the project.

### Operational notes for future troubleshooting

- The dynamic table is **append-only** via this tool — there is no `remove_from_watchlist` MCP tool. To remove a dynamically-added symbol, edit the SQLite DB directly (`DELETE FROM dynamic_watchlist WHERE symbol = ?`) and the collector will drop it on the next cycle.
- `added_by` is free-text. Suggested conventions: `"tis"` (Trigger Ingestion System), `"agent"` (interactive agent session), `"als"` (Alpha Scanner), default `"mcp_client"`.
- If the MCP server can't open the DB read-write (e.g. file permissions, disk full), the tool returns a sanitised error and other read-only tools continue working — `WatchlistWriter` init failure does not poison the `DatabaseReader`.
- The `dynamic_count` returned reflects the post-write total, including any rows pre-existing in the table from prior calls or other callers.
