# TMS-002: Telegram reply poller + agent responder

**Priority:** Medium
**Status:** 🔴 Open
**Component:** `telegram-mcp-server` (new sibling worker or subpackage — tbd in design)
**Created:** 2026-04-23
**Depends On:** TMS-001
**Spec:** _not yet written — requires a new folder under `.kiro/specs/` before implementation_

## Summary

Stand up a long-running process that polls the Telegram bot for incoming replies on a schedule and routes each new message to a Claude-powered responder. The responder should be scoped tightly (allowlisted chat_ids, restricted toolset) and use the existing `telegram-mcp-server` `send_message` / `send_alert` / `edit_message` tools to reply.

This is the layer that turns the MCP server from a one-way notification channel into a conversational agent.

## Motivation

Ad-hoc testing on 2026-04-23 confirmed `get_updates` works end-to-end (reply "Be careful" received from chat_id `2141629529`, update_id `578174315`), but incoming messages are only surfaced on-demand via an MCP tool call. To act on replies asynchronously we need a driver that (a) owns the polling loop and (b) decides what to do with each update.

## Scope

**In scope**
- Scheduled poller process (polling-based, not webhook-based — matches existing architecture).
- Single consumer of `get_updates` (the MCP server's in-process offset is not shared — see Open Questions).
- Per-reply dispatch into a Claude Agent SDK call with the Telegram MCP tools available to the agent.
- Safety controls:
  - **Chat allowlist** — agent only responds to pre-approved chat_ids.
  - **Rate limiting** — cap replies/minute per chat to prevent loops.
  - **System prompt scoping** — narrow persona/instructions, no unbounded tool access.
- Conversation state decision: per-chat history vs stateless (documented in design, not hardcoded here).
- Structured logging of each poll tick and each agent invocation.

**Out of scope**
- Webhook-based delivery (deferred — requires public HTTPS + infra).
- Multi-tenant / multi-bot support.
- Persistent message queue (a DB-backed queue is a follow-up, not the MVP).
- Voice / media reply handling — text only for v1.

## Design notes to carry into the spec

- **Consumer conflict:** `telegram_mcp_server/server.py` tracks `_last_update_offset` as a module-level in-process int. If both the MCP server and the new worker call `getUpdates`, whichever calls first consumes the update and the other sees nothing. Options:
  1. Worker is the sole consumer; the MCP `get_updates` tool is deprecated or restricted to diagnostic use.
  2. Move offset tracking to shared storage (sqlite / file) and make both consumers coordinate.
  3. Worker bypasses the MCP server and talks directly to the Bot API (separate offset, separate token scope).
- **Latency vs cost:** polling interval drives both; 2–5s feels natural for interactive use, but every tick is a Bot API call even when idle. Long-polling (Telegram's `timeout` param on `getUpdates`) is the likely win.
- **Agent runtime:** Claude Agent SDK with `telegram-mcp-server` wired in as a tool source. Consider a minimal tool set (`send_message`, `edit_message`) and omit destructive tools.

## Risks / Open Questions

- **Offset ownership** — see Design notes above. Decision required before coding.
- **Agent prompt injection** — any reply text becomes part of the agent's input. Need to decide on mitigations (system prompt guardrails, role separation, input sanitisation).
- **Loop safety** — if the bot replies to its own messages (e.g. group chats with multiple bots), the rate limit must be per-chat AND the agent must not respond to its own user_id.
- **Cost profile** — every reply triggers an Agent SDK call. Back-of-envelope cost ceiling to be estimated in the design.
