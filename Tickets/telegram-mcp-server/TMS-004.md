## Summary

Originally introduced `scripts/launch-mcp.sh` as a self-healing launcher. During testing on macOS Sequoia, the launcher approach was blocked by two issues:

1. **`com.apple.provenance`** — macOS Sequoia applies a sticky extended attribute to files created by non-system applications (IDEs, editors, agents). This attribute cannot be removed and causes Gatekeeper to block execution with `Operation not permitted`, even with `chmod +x` and even when invoked via `/bin/sh script.sh`.
2. **`UF_HIDDEN` re-application** — the `chflags -R nohidden .venv` command, even when it succeeds, gets silently undone between runs by an unidentified re-applier (possibly IDE automation, backup agent, or indexer).

**Revised approach:** switch to a **non-editable wheel install** (`make install`) which copies the package directly into `site-packages/`, bypassing the `.pth` mechanism entirely. The `UF_HIDDEN` flag becomes irrelevant because Python only checks it on `.pth` files, not on regular `.py` files. MCP client configs point at `.venv/bin/python` directly — no launcher script needed.

## Why

TMS-003 shipped `make venv` and README docs but only reduced risk. Residual holes:

1. Any raw `uv sync` / `uv pip install` / `uv venv` re-applies `UF_HIDDEN` and breaks the next cold start.
2. During the 2026-04-23 diagnosis the flag re-appeared without an explicit `uv` invocation — at least one unidentified background re-applier on the user's machine.
3. No detection or warning at cold-start time.

The launcher was intended to close these gaps but was blocked by Sequoia. The non-editable install eliminates the root cause instead.

## What shipped

### Phase 1 (launcher — superseded)

- **`scripts/launch-mcp.sh`** — POSIX sh, dirname-relative path resolution, silent `chflags 2>/dev/null || true`, `exec` of venv python. Still in the repo but no longer the recommended approach.

### Phase 2 (non-editable install — current)

- **`make install` target** — runs `uv sync`, then `pip install .` (non-editable wheel), then `chflags` cleanup. This is the recommended setup for any machine where the server is launched by an MCP client.
- **README** — Installation section now documents both `make install` (MCP clients) and `make venv` (development). Config snippets point at `.venv/bin/python` directly. Troubleshooting updated with non-editable install as recommended fix and new section for the Sequoia `Operation not permitted` issue.
- **CLAUDE.md Section 3** — documents `make install`, `make venv`, and notes the launcher is blocked by Sequoia.

## Key findings from debugging session

1. **`com.apple.provenance` is not removable** — `xattr -d`, `xattr -c`, and recreating the file via `cat > /tmp/clean && cp` all fail. The attribute persists across copies on Sequoia.
2. **`/bin/sh script.sh` does not bypass provenance** — even passing the script as an argument to `/bin/sh` triggers the same `Operation not permitted`.
3. **`/bin/sh -c "inline commands"` works** — but `chflags` run from within Claude Desktop's sandbox silently fails (the `|| true` swallows the error), so the hidden flag remains.
4. **`PYTHONPATH` does not help** — setting `PYTHONPATH` to the repo root in the MCP client `env` block did not resolve the import when the `.pth` file was hidden. The editable install's meta-path finder was never registered.
5. **Non-editable install is immune** — `pip install .` copies the package as real files into `site-packages/`. Python finds them via normal import machinery without needing `.pth` files. The `UF_HIDDEN` flag on those files is irrelevant.
