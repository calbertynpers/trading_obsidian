## Summary

When the MCP server is launched from Claude Desktop (or any caller whose cwd is not the repo root), startup fails with:

```
/Users/.../telegram-mcp-server/.venv/bin/python: No module named telegram_mcp_server
```

despite `pip list` showing the package as installed editable. Documented the root cause and fix in the README, added a `make venv` target so the workaround is one command, and pointed CLAUDE.md at it so agent sessions don't reinvent the diagnosis.

## Root cause

Three-way interaction:

1. **`uv` on macOS** sets the BSD `UF_HIDDEN` flag on files it writes inside `.venv/` (so Finder hides them). Verifiable with `ls -lO .venv/lib/python3.14/site-packages/` — every entry shows `hidden`.
2. **CPython 3.14's `site.py` was hardened** (`site._process_pth_file`) to skip any `.pth` file carrying `UF_HIDDEN` or the Windows `FILE_ATTRIBUTE_HIDDEN`. Verbose import (`python -v`) shows: `Skipping hidden .pth file: '...__editable__.telegram_mcp_server-0.1.0.pth'`.
3. **Editable installs** rely on that `.pth` running an `import` statement to register a meta-path finder that maps `telegram_mcp_server` → the source tree at the repo root. Skip the `.pth` and the package is unimportable from any cwd other than the repo root (where `python -m` accidentally finds it via `sys.path[0] = ''`).

Claude Desktop launches subprocesses from `$HOME` (or `/`), so it always hits the failure path.

## Fix shipped

- `make venv` runs `uv sync && chflags -R nohidden .venv` in one step.
- README `## Troubleshooting` section walks through the symptom, root cause, and manual `chflags` fix.
- CLAUDE.md Section 3 references `make venv` so agent sessions use the correct setup command.

## Why this keeps coming back

Any of these will re-apply the hidden flag and break startup again:

- `uv sync` / `uv pip install` / `uv pip install -e .`
- Deleting and recreating the venv
- `uv venv`

A fresh checkout on another macOS machine will hit it on day one. `make venv` is the one-step recovery.
