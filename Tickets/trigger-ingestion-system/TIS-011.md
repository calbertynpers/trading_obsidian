## Summary

Build the Lambda function that consumes enriched TriggerEvents from SQS, formats human-readable notifications, and sends them to Telegram. This is the Phase 1 consumer — notifications only, no agent.

Completing this ticket + TIS-004 + one producer (TIS-009 or TIS-010) gives the first end-to-end working system: trigger fires → Telegram notification.

## Scope

- `lambda/event_consumer/handler.py` — Lambda handler (SQS trigger)
- `lambda/event_consumer/notification_formatter.py` — TriggerEvent → Telegram message
- `lambda/event_consumer/telegram_client.py` — Minimal httpx Telegram Bot API client
- `lambda/event_consumer/schemas.py` — TriggerEvent copy for Lambda deployment
- `tests/test_lambda_handler.py` — Handler tests
- `tests/test_notification_formatter.py` — Formatter tests
- `tests/test_telegram_client.py` — Client tests

## Key Design Decisions

- Lambda is synchronous (batch size = 1, no asyncio benefit)
- Concurrency = 1 for sequential processing
- Minimal inline Telegram client (swappable with TMS-005 later)
- Lambda shares TriggerEvent via schema copy (separate deployment unit from EC2 code)
- Failure → exception propagates → SQS retries (3 attempts) → DLQ
- Environment variables for Telegram credentials (TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID)

## Acceptance Criteria

- [ ] Lambda triggered by SQS with batch size = 1
- [ ] Deserialises enriched TriggerEvent from SQS message body
- [ ] Formats notification with: source indicator, symbol, urgency, message, position context
- [ ] Sends formatted notification to Telegram via Bot API
- [ ] Failure raises (SQS retries, then DLQ)
- [ ] Position context routing: has_position true/false/null handled correctly
- [ ] End-to-end: enriched TriggerEvent in SQS → Telegram notification received
