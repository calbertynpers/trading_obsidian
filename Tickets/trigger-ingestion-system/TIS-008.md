# TIS-008: Telegram Synchronous Wait-for-Reply Tool

**Priority:** Medium
**Status:** 🔴 Open
**Component:** `telegram-mcp-server` / `trigger_ingestion_system` — agent return channel
**Type:** Enhancement / tooling
**Reported:** 2026-04-26
**Depends On:** [[TMS-001]], [[TMS-002]]

---

## Summary

Enable the implementation agent to pause and wait for a Telegram reply at decision points, instead of polling on a fixed loop. The agent sends a question via the Telegram MCP, calls a "wait for next message" tool with a timeout, and resumes when the user replies (or the timeout elapses).

---

## Motivation

Async chat between the user and Claude Code over Telegram needs a return channel. A foreground `/loop` polls every N minutes regardless of whether a reply is pending — wasteful on cache and noisy. A synchronous wait fits the natural shape of "I asked a question, I'm blocked until you answer" moments during spec implementation and during live trading-signal triage (TIS confirmation loop, TIS-005).

---

## Acceptance Criteria

- [ ] The Telegram MCP server (or a thin wrapper) exposes a tool that blocks until a new inbound message arrives, with a configurable timeout.
- [ ] Tool returns the message text, sender ID, and timestamp; returns a clear "timed out" sentinel on timeout.
- [ ] Documented usage pattern in `CLAUDE.md` or a steering rule for when to use sync-wait vs. fire-and-forget vs. `/loop` polling.

---

## Out of Scope

- Multi-user routing (single configured chat ID for now).
- Persistent conversation memory across Claude Code sessions.
