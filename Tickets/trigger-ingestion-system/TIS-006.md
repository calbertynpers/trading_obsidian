## Summary

Build the confirmation handling and agent execution layer. A Lambda function receives user CONFIRM/REJECT replies from Telegram (via API Gateway webhook or polling), matches them to pending confirmations in DynamoDB, and on CONFIRM invokes the agent to execute the plan via BDS MCP tools.

## Architecture Context

```
Telegram User Reply
        │
        ▼
API Gateway (or EventBridge + Lambda poll)
        │
        ▼
Lambda "confirmation-handler"
  1. Parse reply (CONFIRM/REJECT, case-insensitive)
  2. Look up pending confirmation in DynamoDB by message_id
  3. If CONFIRM:
     - Publish ExecutionPlan to SQS "execution" queue (priority)
     - Update DynamoDB status = "confirmed"
  4. If REJECT:
     - Update DynamoDB status = "rejected"
     - Send Telegram rejection acknowledgement
        │
        ▼
SQS "execution" queue
        │
        ▼
Lambda "agent-executor"
  1. Deserialise confirmed ExecutionPlan
  2. Invoke agent with plan + "execute this confirmed plan" instruction
  3. Agent calls BDS MCP tools (place_market_order, place_stop_order, etc.)
  4. Send execution receipt to Telegram
  5. On failure: send error notification to Telegram
```

## Key Design Decisions

1. **Telegram reply delivery** — Two options:
   - **(A) API Gateway webhook**: Configure Telegram Bot API `setWebhook` to POST updates to an API Gateway endpoint → Lambda. Real-time, no polling.
   - **(B) EventBridge scheduled Lambda**: Poll TMS-002 `getUpdates` every 3 seconds via EventBridge rule → Lambda. Simpler setup, slight latency.
   
   **Recommendation:** Start with (B) for simplicity. Migrate to (A) when latency matters.

2. **DynamoDB for pending confirmations** — Schema:
   ```
   PK: trigger_id (String)
   message_id: (Number) — Telegram message_id for reply correlation
   execution_plan: (String) — JSON serialised ExecutionPlan
   status: (String) — "pending" | "confirmed" | "rejected" | "expired"
   created_at: (Number) — epoch seconds
   ttl: (Number) — epoch seconds + confirmation_timeout_min * 60
   ```
   DynamoDB TTL auto-deletes expired items → handles timeout without a separate handler.

3. **Reply correlation via message_id** — The confirmation handler looks up DynamoDB by scanning for `message_id` match (GSI on `message_id`). Duplicate replies on resolved confirmations are ignored (status != "pending").

4. **Separate execution queue** — Confirmed plans go to a dedicated SQS "execution" queue. This gives priority over new trigger evaluations (the agent-dispatcher Lambda on the trigger queue has concurrency=1, so execution doesn't wait behind new evaluations).

5. **Agent executes via MCP tools** — The agent-executor Lambda invokes the agent with the confirmed ExecutionPlan and a system prompt instructing it to execute. The agent calls BDS MCP tools (running on EC2) via HTTP.

6. **Execution receipt** — After successful execution, the agent sends a receipt to Telegram with order IDs, fill prices, and status.

## Acceptance Criteria

- [ ] User CONFIRM reply matched to pending confirmation in DynamoDB
- [ ] User REJECT reply updates DynamoDB status and sends acknowledgement
- [ ] Duplicate replies on resolved confirmations ignored (logged at DEBUG)
- [ ] Case-insensitive matching of CONFIRM/REJECT
- [ ] Confirmed plan published to SQS "execution" queue
- [ ] Agent-executor Lambda invokes agent with confirmed plan
- [ ] Agent executes via BDS MCP tools (place_market_order, etc.)
- [ ] Execution receipt sent to Telegram with order details
- [ ] Execution failure → error notification to Telegram, no retry
- [ ] DynamoDB TTL expires pending confirmations after timeout
- [ ] Expired confirmations → timeout notification to Telegram (via DynamoDB Streams or EventBridge)
- [ ] confirm_all enforced — agent only executes after explicit CONFIRM
