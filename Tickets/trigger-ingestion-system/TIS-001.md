## Summary

Build a unified trigger ingestion system that accepts price-based signals from two sources — an internal polling daemon and external TradingView webhook alerts — normalises them into a common event schema, enriches them with live position context, and dispatches them to an agent for evaluation. The agent broadcasts a proposed action to Telegram; the user confirms or rejects; the agent executes via Binance. The TV alert message itself acts as the agent prompt, enabling rich, indicator-based instructions authored once in TradingView and executed end-to-end with a single confirmation.

---

## Problem

There is currently no system to:
- Detect price or indicator conditions in near-real-time and act on them
- Accept rich, multi-indicator signals from TradingView alongside simple internal price thresholds
- Deliver a proposed trade action to the user for confirmation before execution
- Handle the full loop: signal → agent evaluation → human confirmation → Binance execution
- Allow the Alpha scanner to dynamically register new symbols for monitoring without service restart

## Trigger Sources

### External Triggers — TradingView Webhooks

TradingView alerts are configured in the TV UI using any combination of indicators (RSI, Bollinger Bands, MACD, custom Pine Script, volume, etc.). When an alert fires, TV POSTs a JSON payload to the system's webhook endpoint.

**Key design point:** The TradingView alert message template IS the agent prompt. When setting up an alert in TV, the message field is authored as a trading instruction:

```
Enter LONG ZKJUSDT, 5x leverage, $15 collateral. TP1: $0.0175 | TP2: $0.0195 | TP3: $0.0215. SL: $0.0135.
Mean reversion signal: Weekly RSI 19.9, Daily RSI 27, 4H RSI 19.65 — all extreme oversold.
```

The agent receives this message as its instruction, enriches it with live position data, and constructs a full execution plan for confirmation. No separate prompt-authoring step required.

**External trigger characteristics:**
- Analytically rich — complex indicator confluence baked into the condition
- Set up manually in TV UI (no API for programmatic alert creation)
- Delivered as webhook POST to the system's `/webhook` endpoint
- Message contains both the trading instruction and the analytical rationale
- Suitable for: mean reversion signals, breakout confirmations, multi-timeframe confluence

### Internal Triggers — Price Condition Monitor

A polling daemon queries the Binance REST batch price endpoint (`GET /fapi/v1/ticker/price`) at a configurable interval (default: 5 seconds) and evaluates conditions stored in SQLite.

**Internal trigger characteristics:**
- Simple, programmatic — `gt`, `lt`, `gte`, `lte` operators on price
- Created programmatically — agents, Alpha scanner (ALS-001), or manual DB write
- Dynamic watchlist — new symbols registered externally without service restart
- Suitable for: stop-loss threshold breach, risk monitoring, position management events, Alpha scanner candidate tracking

## Normalised Trigger Event Schema

All triggers — regardless of source — are normalised into a common `TriggerEvent` before dispatch:

```python
@dataclass
class TriggerEvent:
    trigger_id:     str        # UUID
    source:         str        # 'tradingview' | 'internal'
    trigger_type:   str        # 'indicator_confluence' | 'price_threshold' | 'pct_change' | 'risk_alert'
    symbol:         str        # e.g. 'ZKJUSDT'
    timestamp:      str        # ISO8601
    urgency:        str        # 'info' | 'alert' | 'action_required'
    message:        str        # agent prompt (TV message or generated from condition)
    raw_payload:    dict       # original TV JSON or condition row
    context:        dict       # enriched: position size, entry price, PnL, margin, open orders
    suggested_action: str | None  # extracted from message if parseable
```

**How source affects handling:**

| Aspect | External (TradingView) | Internal (Price Monitor) |
|--------|----------------------|--------------------------|
| Message | Authored in TV UI by trader — rich, contextual | Auto-generated from condition: "HIGHUSDT LONG has breached -30% stop threshold" |
| Agent prompt | Message is used directly | Message is used directly |
| Urgency | Set by trader in TV message template | Derived from condition type (`risk_alert` = `action_required`) |
| Suggested action | Parsed from structured fields in message | Derived from condition label + type |
| Cooldown | Not applicable (TV manages) | Enforced via `last_fired` in SQLite |

## Telegram Confirmation Loop

The agent broadcasts a proposed action to Telegram and waits for the user's reply before executing. This depends on [[TMS-001]] (send) and [[TMS-002]] (reply poller).

**Flow:**

```
TriggerEvent received by agent
  ↓
Agent evaluates instruction + enriched context
  ↓
Agent sends Telegram message:

  📡 Signal: LONG ZKJUSDT [TradingView]
  ─────────────────────────────
  Entry:  $0.0155 (market)
  Size:   $15 collateral @ 5x → 4,839 units
  TP1:    $0.0175  |  TP2: $0.0195  |  TP3: $0.0215
  SL:     $0.0135
  ─────────────────────────────
  Rationale: Weekly RSI 19.9, Daily RSI 27, 4H 19.65 — extreme oversold
  ─────────────────────────────
  Reply CONFIRM to execute · REJECT to cancel
  ─────────────────────────────
  Expires in 15 minutes

  ↓
TMS-002 reply poller receives user reply
  ↓
CONFIRM  → agent executes: market order + TP orders + SL placed
REJECT   → cancelled, logged
Modify   → e.g. "CONFIRM $10" → agent recalculates, re-presents for confirmation
Timeout  → cancelled after N minutes, alert sent: "⏱ Signal expired — no confirmation received"
  ↓
Execution receipt via Telegram:

  ✅ Executed: 4,839 units LONG ZKJUSDT at $0.01552
  Stop: $0.0135 · TP1: $0.0175 · TP2: $0.0195 · TP3: $0.0215
```

**Confirmation keywords:**
- `CONFIRM` — execute as proposed
- `CONFIRM <amount>` — execute with modified collateral (agent recalculates and re-presents)
- `REJECT` — cancel, log reason optional
- `SKIP` — dismiss without logging as rejection

**Timeout behaviour:** configurable `confirmation_timeout_min` (default: 15). On expiry, trigger is cancelled and logged. A Telegram notification is sent.

## Internal Trigger: Data Model

```sql
-- Watchlist: externally writable by Alpha scanner, agents, or manual entry
CREATE TABLE watchlist (
  symbol      TEXT PRIMARY KEY,
  added_by    TEXT,   -- 'alpha_scanner' | 'agent' | 'manual'
  added_at    TEXT DEFAULT (datetime('now')),
  active      INTEGER DEFAULT 1
);

-- Conditions: trigger definitions
CREATE TABLE conditions (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  symbol       TEXT NOT NULL,
  operator     TEXT NOT NULL,     -- 'gt' | 'lt' | 'gte' | 'lte'
  threshold    REAL NOT NULL,
  trigger_type TEXT DEFAULT 'price_threshold',
  urgency      TEXT DEFAULT 'alert',
  action       TEXT DEFAULT 'telegram',   -- 'telegram' | 'agent_notify' | 'agent_execute'
  cooldown_sec INTEGER DEFAULT 300,
  active       INTEGER DEFAULT 1,
  label        TEXT,                      -- human-readable: "HIGHUSDT 30% stop breach"
  last_fired   TEXT,                      -- ISO8601 — persisted across restarts
  created_at   TEXT DEFAULT (datetime('now'))
);
```

**Cooldown state persists across restarts** — `last_fired` is loaded from SQLite on startup so cooldowns are honoured after crashes.

## Phase 1 Scope (MVP)

**Internal trigger path:**
- [ ] REST price fetcher — batch endpoint, configurable `poll_interval_sec`
- [ ] SQLite watchlist table — externally writable, polled on refresh cycle
- [ ] SQLite conditions table — `gt`, `lt`, `gte`, `lte` operators, CRUD without restart
- [ ] Condition evaluator with cooldown, `last_fired` persisted across restarts
- [ ] Trigger normaliser — produces `TriggerEvent` from condition match
- [ ] Enrichment layer — appends live position data from Binance API

**External trigger path:**
- [ ] Webhook receiver — HTTP POST endpoint, parse TradingView JSON payload
- [ ] TV payload parser — extracts symbol, message, urgency from TV format
- [ ] Same trigger normaliser and enrichment layer as internal path

**Dispatch:**
- [ ] Telegram dispatch — formats `TriggerEvent` as Telegram message via TMS-001
- [ ] Confirmation listener — polls for CONFIRM/REJECT via TMS-002 `get_updates`
- [ ] Timeout handler — cancels pending confirmations after `confirmation_timeout_min`

## Phase 2 Scope

- [ ] Agent dispatch — routes `TriggerEvent` to Claude agent session with full context
- [ ] Agent parses message, builds execution plan, presents via Telegram, executes on CONFIRM
- [ ] Modify flow — `CONFIRM $10` recalculates and re-presents before executing
- [ ] Additional internal condition types: `pct_change_1m`, `pct_change_5m`

## Phase 3 Scope (AgentCore)

- [ ] AgentCore deployment as the persistent autonomous agent runtime
- [ ] Binance MCP tools adapted as AgentCore Tool Gateway tools (primary engineering task)
- [ ] Cedar policy definitions for trading guardrails (max notional, confirmation requirements)
- [ ] Fully headless overnight operation — agent receives triggers, evaluates, executes autonomously within Cedar bounds
- [ ] CloudWatch dashboard for trigger volume, confirmation rates, execution outcomes
- [ ] TIS-002: MySQL migration (separate ticket)

- [ ] Internal: a `price_lt` condition fires a Telegram message when price crosses threshold
