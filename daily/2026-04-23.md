## TMS-001 — Telegram MCP Server — Kickoff

Started the `telegram-mcp-server` project — standalone FastMCP + stdio wrapper around the Telegram Bot API. Five tools: `send_message`, `send_alert`, `get_updates`, `edit_message`, `send_photo`. Thin, stateless — no dedup / rate-limit / filter.

**Spec:** `.kiro/specs/telegram-mcp-server/` (requirements + design + tasks authored in Kiro).

**Status:** TMS-001 ticket opened; scaffolding is next (pyproject.toml, package skeleton, test deps). Tasks 1–10 tracked in repo `tasks.md`.

**Key design calls (from spec):**
- FastMCP + stdio transport; matches coingecko-scanner / binance-data-collector pattern.
- `httpx.AsyncClient` with 10s timeout; non-200 / `HTTPError` returns typed error dict — never crashes.
- `pydantic-settings` for `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`; validates at import, fails fast.
- Alert formatting is pure (`format_alert` / `parse_alert`), HTML-escaped, round-trip testable via Hypothesis.
- Only in-memory state: `_last_update_offset` for `getUpdates` cursoring; resets on restart.

See [[TMS-001]] for acceptance criteria, [[Trading/telegram-mcp-server/Overview|Overview]] and [[Trading/telegram-mcp-server/Technical Notes|Technical Notes]] for project-level context.

## telegram-mcp-server — Claude Desktop startup failure (2026-04-23)

**Symptom:** Claude Desktop logs `No module named telegram_mcp_server` despite editable install showing in `pip list`. Server transport closes immediately.

**Root cause:** Three-way interaction between (1) `uv` setting macOS `UF_HIDDEN` flag on files inside `.venv/`, (2) Python 3.14's hardened `site._process_pth_file` skipping any `.pth` file with `UF_HIDDEN`, and (3) the editable install relying on that `.pth` to register a meta-path finder for `telegram_mcp_server`. Verified via `python -v` showing `Skipping hidden .pth file: '...__editable__.telegram_mcp_server-0.1.0.pth'`. From repo cwd it accidentally works (cwd in `sys.path`); Claude Desktop launches from `$HOME` so it always fails.

**Fix applied:** `chflags -R nohidden /Users/clintalbertyn/Documents/repos/telegram-mcp-server/.venv` — verified `import telegram_mcp_server` now succeeds from `/tmp`. User to restart MCP server in Claude Desktop.

**Caveat:** Any subsequent `uv sync` / `uv pip install` / `uv venv` will re-apply the hidden flag and re-break startup.

**Follow-up:** Filed [[TMS-003]] — document workaround in `README.md`, add a `make venv` (or equivalent) target that bundles `uv sync && chflags -R nohidden .venv`, reference it from `CLAUDE.md` Section 3.

## TMS-004 — Opened (2026-04-23)

Follow-up to TMS-003. Post-implementation review surfaced residual risk: `make venv` only helps if humans/tools remember to use it. Any raw `uv` invocation re-introduces `UF_HIDDEN`, and we observed at least one unidentified re-applier during this session.

**Proposal:** `scripts/launch-mcp.sh` wrapper that runs `chflags -R nohidden .venv` then `exec`s the venv python with `-m telegram_mcp_server`. Claude Desktop / Claude Code configs point `command` at the wrapper. Every cold start self-heals — the failure mode is removed at the boot path rather than mitigated via memory.

Spec not yet written. Acceptance criteria and design notes captured in the ticket; next step is Kiro spec folder `.kiro/specs/TMS-004/`.

## TMS-004 — Revised (2026-04-23)

Original launcher script approach (`scripts/launch-mcp.sh`) blocked by two macOS Sequoia issues:
1. `com.apple.provenance` — sticky extended attribute blocks execution of files created by IDEs/agents. Cannot be removed.
2. `chflags` run from Claude Desktop's sandbox silently fails — hidden flag persists.

Switched to **non-editable wheel install** (`make install` = `uv sync` + `pip install .`). Copies package into `site-packages/` directly, bypassing `.pth` mechanism entirely. `UF_HIDDEN` becomes irrelevant. Confirmed working in Claude Desktop.
